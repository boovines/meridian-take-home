# Draft review and frozen handoff

Implemented behavior; engineer generation and execution remain separate features.

A customer opens Review & comments, requests review, and sees the canvas become read-only. A missing workflow outcome creates a clarification thread; the supplied answer updates the workflow before analysis. Otherwise Temporal starts review in the background. Cancellation immediately unlocks the board and prevents late publication. Failed or abandoned queued/running reviews unlock after a recorded five-minute deadline is observed; the UI polls while active.

The OpenAI reviewer receives process content and discussion history. It can ask about ambiguity, inconsistent behavior, missing exceptions, and unnecessary steps. It cannot mutate the graph. Results are schema-checked and published in one transaction against the sealed draft revision. Invalid anchors or attempts to follow up a closed thread reject the publication. A closed concern can be represented by a linked new finding after process content changes; relevance of that change is judged by the reviewer prompt, not a deterministic semantic proof.

One response field supports Reply, Resolve or Reject, with the response recorded as the comment or decision reason. The chip starts Open, becomes Answered after a customer reply, and shows Resolved or Rejected after that decision. Reopening resets it to Open; earlier replies remain in history.

Sending Reply on an AI finding saves the answer and an AI response containing proposed instruction changes. It does **not** change the blocks. The response shows a word-level diff for each affected block, with additions and removals distinguished by text styling and a legend. The process expert chooses **Accept changes** or **Reject changes**. Acceptance saves every proposed edit together and updates the canvas in place; rejection keeps every block unchanged. Both decisions remain in the conversation with the original answer and proposed diff. A new reply supersedes the preceding proposal. If the board changes before acceptance, the expert must reply again for a fresh proposal; stale proposals can still be rejected. Neither decision resolves the finding: Resolve and Reject in the response selector remain separate finding decisions and never invoke a rewrite. The initial reviewer detail suggestion still offers Apply and resolve.

The model may propose instruction changes across multiple referenced blocks, preserving unrelated requirements, route semantics and human approvals. It cannot change graph structure. A reply clears the initial review suggestion to prevent applying an obsolete alternative. No database migration is needed: the existing ordered discussion history retains proposals, before/after evidence and decisions.

Review & comments keeps all conversations together. Each finding or note has an Expand conversation button beside its status chip. It opens that conversation in a larger modal with the same messages, references, proposed diffs, actions and response draft. Distinct author labels, avatars and reply bubbles identify the expert and AI. Closing or pressing Escape restores focus to the expand button and preserves the draft; there is only one active composer. Keyboard focus stays inside the expanded view. Opening and closing are immediate, including under reduced motion.

The rewrite is a bounded foreground request (90 seconds), with model calls outside SQL transactions. Proposal publication checks the workflow content revision, target revisions, thread revision and editable state again. Acceptance repeats these checks before saving any block edits. A concurrent edit, new review, timeout, invalid output or provider failure saves no partial reply/proposal; the response field remains available for retry. Request keys deduplicate committed retries, including a lost HTTP response. Concurrent uncommitted duplicate requests may both invoke the model, but publish only once; there is no durable background operation or automatic resume after a disconnected request.

Workflow-only/connection-only findings and removed targets retain the answer with an explicit manual-update explanation. Ambiguous answers or already-incorporated details can record no change; graph changes remain manual. These outcomes never claim a block update. Ordinary discussion notes remain comments. Accepted instructions flow through subsequent review snapshots and the frozen graph used for generation; semantic changes still require a new review or explicit handoff acknowledgment. Model preservation of unrelated meaning is prompt-directed, not a deterministic semantic guarantee.

Messages have parent IDs and per-thread ordering. Resolutions and reopens append history. The customer must explain a manual resolution or rejection; accepting a detail suggestion changes only title/instructions and closes the finding atomically. A stale node revision rejects the entire operation. Ordinary customer notes do not block freeze. Removing a finding's only referenced node closes it with a deletion reason; other findings remain available for a decision.

Hovering a finding or discussion thread highlights its referenced blocks and connections on the canvas without changing the selected item. Keyboard focus within the thread does the same. Highlights clear when leaving the thread or closing the panel; workflow-wide comments highlight the whole graph. Referenced-item links remain available in a compact disclosure, including removed-item context.

Freeze requires a nonblank outcome, one Trigger, an explicit Outcome, reachable active blocks, valid endpoints and routing, paired nonoverlapping parallel sections, a completed review, and no open findings. Later semantic edits require acknowledgment or another review. Position-only changes do not require acknowledgment. The immutable snapshot contains the graph and review decisions. Database triggers protect the frozen graph and specification. Post-handoff revisions are outside this demo.

The workflow row serializes mutations to that workflow; other workflows proceed independently. Model calls occur outside SQL transactions. Review IDs, rather than shipment/process payloads, pass through Temporal. An activity can retry after worker failure; a completed publication is idempotent, and a duplicate API request key returns the original run. If initial dispatch fails, the board is unlocked with an actionable failure. Queued review rows also serve as durable dispatch intents: the worker reconciles them every five seconds with stable Temporal IDs. A crash between commit and dispatch is retried; a review whose deadline expires is marked failed instead of leaving the canvas locked.

Verification: reply tests cover unchanged blocks before approval, multi-block atomic acceptance, rejection, superseded and stale proposals, competing decisions, before/after audit and frozen handoff, failed inference, stale inputs, cancellation, invalid targets/output, lost-response retries and manual outcomes. Browser tests cover unchanged cards before approval, immediate accepted card updates, decisions and instructions on reopen, preserved drafts on errors and expansion, keyboard focus, Escape, rapid open/close, reduced motion and narrow-screen layout. Provider-contract tests use mocked inference; the local fixture rewrite does not establish live model quality. Existing persistence tests cover cancellation, stale application, goal clarification, history, deletion, rollback, deadline recovery, and frozen mutation rejection; graph tests cover loops and paired parallelism; browser tests cover two review rounds, approval, handoff and cancellation. CI uses an explicitly marked fixture reviewer. A separate live check verified Supabase → Temporal Cloud worker → OpenAI → persisted finding.

Known demo limits: review history displays the latest 20 runs; conversation pagination is deferred. Unsaved comment text is kept on request errors, but closing the panel discards it. Human comment creation supports the current selection or the whole workflow; AI findings can anchor multiple elements. No notifications, assignments, permissions, realtime collaboration or post-freeze edits are included.
