# Draft review and frozen handoff

Implemented behavior; engineer generation and execution remain separate features.

A customer opens Review & comments, requests review, and sees the canvas become read-only. A missing workflow outcome creates a clarification thread; the supplied answer updates the workflow before analysis. Otherwise Temporal starts review in the background. Cancellation immediately unlocks the board and prevents late publication. Failed or abandoned queued/running reviews unlock after a recorded five-minute deadline is observed; the UI polls while active.

The OpenAI reviewer receives process content, discussion history, and any explicitly saved [optional process context](whiteboard-authoring.md#optional-process-context). Raw observations are sealed with the review input, treated as untrusted evidence, and kept outside executable instructions. It can ask about ambiguity, inconsistent behavior, missing exceptions, and unnecessary steps. It cannot mutate the graph. Results are schema-checked and published in one transaction against the sealed draft revision. Invalid anchors or attempts to follow up a closed thread reject the publication. A closed concern can be represented by a linked new finding after process content changes; relevance of that change is judged by the reviewer prompt, not a deterministic semantic proof.

Long review histories are projected losslessly into the model input: repeated long strings are stored once in a text dictionary and referenced from their original locations. This preserves the supplied board, customer wording, proposals and decision evidence without duplicating instruction snapshots. The database history is unchanged. Inputs that still exceed 180 KB fail with a specific explanation that retrying unchanged context will not help; the draft remains editable and unchanged, and this deterministic failure is not retried. Reviewer version `process-review-v3` identifies this prompt representation.

One response field supports Reply, Resolve or Reject, with the response recorded as the comment or decision reason. The chip starts Open, becomes Answered after a customer reply, and shows Resolved or Rejected after that decision. Reopening resets it to Open; earlier replies remain in history.

Sending Reply on an AI finding saves the answer and an AI response containing proposed instruction changes. It does **not** change the blocks. Each affected block has an editable instructions textbox, an always-visible live word-level diff against the original instructions, and its own **Accept changes** and **Reject changes** controls. The diff reflects the expert’s edited wording: AI and human additions are green, removed original text is struck through, and unchanged text stays neutral. Editing away an AI-only addition removes it from the comparison rather than treating it as original text. The expanded view pairs the editor and diff in equal-width, equal-height panes with aligned headers and independently scrolling content; narrow screens and the all-comments panel stack them. Acceptance saves only that block’s final wording and updates the canvas in place; rejection leaves that block unchanged. Other blocks remain pending, including their unsaved text. Blank or over-limit accepted instructions are disallowed. Decisions remain in the conversation with the original answer, AI proposal and actual saved wording. Human edits to accepted proposals retain the original AI suggestion in a separate disclosure. A new reply supersedes the preceding proposal. Accepting a sibling block from the same proposal does not invalidate remaining blocks. If an unrelated board change occurs before acceptance, the expert must reply again for a fresh proposal; stale proposals can still be rejected. Neither decision resolves the finding: Resolve and Reject in the response selector remain separate finding decisions and never invoke a rewrite. The initial reviewer detail suggestion still offers Apply and resolve.

The model may propose instruction changes across multiple referenced blocks, preserving unrelated requirements, route semantics and human approvals. It cannot change graph structure. A reply clears the initial review suggestion to prevent applying an obsolete alternative. No database migration is needed: the existing ordered discussion history retains proposals, before/after evidence and decisions.

Review & comments keeps all conversations together. Each finding or note has an Expand conversation button beside its status chip. It opens that conversation in a larger modal with the same messages, references, editable proposals, actions and response draft. Distinct author labels, avatars and reply bubbles identify the expert and AI. Closing or pressing Escape restores focus to the expand button and preserves reply and proposal drafts; there is only one active composer. Keyboard focus stays inside the expanded view. Opening and closing are immediate, including under reduced motion.

The rewrite is a bounded foreground request (90 seconds), with model calls outside SQL transactions. Proposal publication checks the workflow content revision, target revisions, thread revision and editable state again. Each block acceptance rechecks the target revision and workflow content revision, accounting only for already accepted sibling blocks from the same proposal. A concurrent edit, new review, timeout, invalid output or provider failure saves no partial reply/proposal; the response field remains available for retry. Request keys deduplicate committed retries, including a lost HTTP response. Concurrent uncommitted duplicate requests may both invoke the model, but publish only once; there is no durable background operation or automatic resume after a disconnected request.

Workflow-only/connection-only findings and removed targets retain the answer with an explicit manual-update explanation. Ambiguous answers or already-incorporated details can record no change; graph changes remain manual. These outcomes never claim a block update. Ordinary discussion notes remain comments. Accepted instructions flow through subsequent review snapshots and the frozen graph used for generation; semantic changes still require a new review or explicit handoff acknowledgment. Model preservation of unrelated meaning is prompt-directed, not a deterministic semantic guarantee.

Messages have parent IDs and per-thread ordering. Resolutions and reopens append history. The customer must explain a manual resolution or rejection; accepting a detail suggestion changes only title/instructions and closes the finding atomically. A stale node revision rejects the entire operation. Ordinary customer notes do not block freeze. Removing a finding's only referenced node closes it with a deletion reason; other findings remain available for a decision.

Hovering a finding or discussion thread highlights its referenced blocks and connections on the canvas without changing the selected item. Keyboard focus within the thread does the same. Highlights clear when leaving the thread or closing the panel; workflow-wide comments highlight the whole graph. Referenced-item links remain available in a compact disclosure, including removed-item context.

Freeze requires a nonblank outcome, one Trigger, an explicit Outcome, reachable active blocks, valid endpoints and routing, paired nonoverlapping parallel sections, a completed review for the current process revision, and no open findings or engineer requests for that revision. Later semantic edits require acknowledgment or another review. Position-only changes do not require acknowledgment. The immutable snapshot contains the graph and review decisions. Database triggers protect the frozen graph and specification. Post-handoff changes use an explicit new draft and preserve the approved version; see [process revisions](engineer-generation.md#engineer-requested-process-revisions).

Freeze diagnostics name a misplaced parallel wait block and the path that cannot reach it. A single explanation replaces the cascading unreachable/end-of-process warnings for that pairing. For a simple pair of branches already connected to one shared next block, numbered instructions identify the exact “Wait for both paths from” settings to clear and set, with an Edit button opening each block. After clearing the incorrect setting, the remaining warning still points to that shared block. More complex graphs receive connection/setting guidance without guessing where they should join. These are manual corrections; diagnostics never rewrite the graph or bypass review and freeze checks.

The workflow row serializes mutations to that workflow; other workflows proceed independently. Model calls occur outside SQL transactions. Review IDs, rather than shipment/process payloads, pass through Temporal. An activity can retry after worker failure; a completed publication is idempotent, and a duplicate API request key returns the original run. If initial dispatch fails, the board is unlocked with an actionable failure. Queued review rows also serve as durable dispatch intents: the worker reconciles them every five seconds with stable Temporal IDs. A crash between commit and dispatch is retried; a review whose deadline expires is marked failed instead of leaving the canvas locked.

Verification: reply tests cover unchanged blocks before approval, independent block acceptance and rejection, human-edited saved wording, superseded and stale proposals, competing decisions, before/after audit and frozen handoff, failed inference, stale inputs, cancellation, invalid targets/output, lost-response retries and manual outcomes. Browser tests cover unchanged cards before approval, immediate accepted card updates, decisions and instructions on reopen, preserved reply and proposal drafts on errors and expansion, keyboard focus, Escape, rapid open/close, reduced motion and narrow-screen layout. Provider-contract tests use mocked inference; the local fixture rewrite does not establish live model quality. Existing persistence tests cover cancellation, stale application, goal clarification, history, deletion, rollback, deadline recovery, and frozen mutation rejection; graph tests cover loops and paired parallelism; browser tests cover two review rounds, approval, handoff and cancellation. CI uses an explicitly marked fixture reviewer. A separate live check verified Supabase → Temporal Cloud worker → OpenAI → persisted finding.

Known demo limits: review history displays the latest 20 runs; conversation pagination is deferred. Unsaved comment text is kept on request errors, but closing the panel discards it. Human comment creation supports the current selection or the whole workflow; AI findings can anchor multiple elements. No notifications, assignments, permissions, realtime collaboration or direct edits to frozen specifications are included.

If a reply response is lost, an unchanged retry retains the original request key, thread revision and parent message even if another refresh has advanced the visible discussion. A definitive stale-context rejection allows the next attempt to use the refreshed context.

The comparison diff is a named keyboard-focusable region, so long instructions can be scrolled with the keyboard inside the equal-height panes. At narrow widths the panes stack vertically.
